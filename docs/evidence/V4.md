# V4 — batch and cost control

**Status: PARTIAL.** The batch mechanism, its cost accounting and the L0
pre-filter are implemented and have run on real subjects. V4's stated acceptance
— *a batch of 20 plugins runs in CI with predictable cost and no credential
leak* — has **not** been met: the largest batch run so far is **4** subjects.

## 2. The finding that matters: a false pass, and how it hid

`@morlay/session-branch@0.1.5` declares no `dsh.bundle.patch`. It is not a
plugin. The first batch run published this:

```
npm:@morlay/session-branch@0.1.5   not-installable
  L0=fail  L1=pass  L2=pass  L3=pass  L4=pass  L5=pass  L6=pass
```

The headline was right — L0 failed, so the verdict was `not-installable` — but
**six execution dimensions claimed success on a subject that was never
composed**. `dsh plugin add` returns 0 because the package installs fine *as a
plain dependency*; the profile then boots, a session runs, and removal leaves
nothing, because the subject was never in the tree. Every measurement was of the
subject's absence, reported as its success.

This is the second false pass this project has produced (the first was the
profile path in V1). Both had the same shape: **a pass derived from the absence
of a failure rather than the presence of the subject.**

### The fix, in two places

1. **`packages/report/src/merge.ts`** — `declaresBundle()` reads the L0 metrics
   and, when false, forces L1–L6 to `skip` with an explicit reason, and drops any
   `overhead` object. It runs *after* the execution dimensions are assigned, so
   it overrides whatever execution claimed.
2. **`run-suite.sh`** — the same judgement is applied *before* starting a
   container, so a non-bundle costs a static fetch and nothing else. That is the
   L0 pre-filter the specification asks for, and it is also the cost saving.

A bundle whose declared patch path is missing from the tarball is still a
bundle: its install or load can fail informatively, so execution is worth
running. That distinction is asserted by a test.

## 3. Measured cost

Run `37134939704`, 4 subjects, sequential, one container each:

| Subject | Verdict | Seconds |
|---|---|---|
| `dsh-pet@0.3.1` | `verified` | 95 |
| `dsh-cost-meter@1.8.8` | `verified` | 94 |
| `@morlay/session-branch@0.1.5` | `not-installable` | 94 |
| `dsh-find-plugin@0.4.0` | `partial` | 33 |

Total 6m12s of job time for 4 subjects. The interesting number is not the mean
but the **shape**: roughly 90 s per subject, almost all of it the L5 differential
(6 sampled runs) and the L3 setup (a headless profile plus two installs). The
find-plugin subject was cheapest precisely because it failed at L1 and skipped
everything downstream.

`@morlay/session-branch` cost 94 s here and would now cost a few seconds: that
row is the pre-filter's justification, and it was found by measuring rather than
by reasoning.

At ~90 s per subject, the specification's 20-subject acceptance is roughly
**30 minutes** of sequential CI, which is affordable but argues for either a
concurrency cap above 1 or a cheaper L5 pass. That decision is deferred, not
made.

## 4. What the batch produced

```
index: {verified: 2, partial: 1, not-installable: 1}
  npm:dsh-cost-meter@1.8.8           verified          all seven pass
  npm:dsh-pet@0.3.1                  verified          all seven pass
  npm:dsh-find-plugin@0.4.0          partial           L1 refused: peer-incompatible
  npm:@morlay/session-branch@0.1.5   not-installable   L0 fail; L1-L6 pre-filtered
```

`dsh-pet@0.3.1` is the second `verified` report, and a useful one: a 62 MB
client plugin with four capability signals including `listens_on_port` and
`spawns_process`.

The batch also discharged a debt from earlier rounds: `catalog/npm/dsh-find-plugin.json`
had been carrying the **retracted** claim that L3 was blocked because the replay
adapter is uninstallable. Regenerating it replaced that with `skip`, which is
what an L1 refusal actually implies.

## 5. Verified / not verified

**Verified:** batches run; per-subject ceilings hold; a failing subject does not
abort the batch; cost is measured per subject; a non-bundle cannot collect
execution passes; the catalogue is regenerated consistently from a batch.

**Not verified:** any batch larger than 4; behaviour under concurrency; retry
behaviour; that the per-subject ceiling actually fires (no subject has hit it).

**Not implemented:** retry-once-then-abandon, concurrency above 1, the subject
survey, the curated pool.

## 6. Remaining prerequisites

1. **The 20-subject acceptance run.** Requires a subject list first.
2. **The survey and its by-product.** Source subjects from the npm `dsh-plugin`
   keyword set and the GitHub topic, and publish the figure the specification
   asks for: how many of them are actually installable bundles. The L0
   pre-filter makes this cheap — metadata and a tarball read, no container.
3. **A curated pool** with priority ordering, per the specification's
   "curated pool first, then on demand".
4. **Retry policy**: retry once, then record `inconclusive` rather than failing.
5. **A concurrency decision**, now that ~90 s/subject is measured.

## 7. Reproduce

```sh
gh workflow run verify.yml -f dsh_version=0.2.0-rc.2 \
  -f verify_specs='dsh-cost-meter@1.8.8,dsh-find-plugin@0.4.0,@morlay/session-branch@0.1.5,dsh-pet@0.3.1'
gh run download <run-id> -n exec-reports
cat .verify/reports/timings.tsv
node --test packages/report/test/*.test.ts
```
