## 2. The acceptance run

20 subjects, one after another, one container each.

| Verdict | Count |
|---|---|
| `verified` | **17** |
| `partial` | 3 |

### Cost

| | |
|---|---|
| Total wall time | 31 minutes |
| Median per subject | **94 s** |
| Range | 36 s – 100 s |
| Slowest | `dsh-tiddlywiki@0.30.57`, 100 s |

The distribution is remarkably flat, and the flatness is the finding: cost is
dominated by **fixed setup**, not by the subject. Every verified subject pays
for the L5 differential (6 sampled boots) and the L3 setup (a headless profile
plus two installs) regardless of what it is. The three cheapest runs are the
failures — 36–39 s — because they stopped at L1.

A 20-subject batch at ~94 s is 31 minutes, which fits the 60-minute job timeout
with room to spare. **That is the cost model, measured.**

### The three that were not verified

Three *different* reasons:

| Subject | Dimension | Reason |
|---|---|---|
| `@roarpeng/graphflow@2.2.0` | L1 | installation blocked pending dependency build-script approval |
| `dsh-codex-connect@0.2.0-alpha.1` | L1 | same |
| `@wxg-prc-cpg/browser-skill-dsh-plugin@0.3.2` | L2 | the composition reported a failure at boot |

The first two are the specification's "pending build scripts" case, and the
report names what pnpm refused to run:

```
Ignored build scripts: @roarpeng/graphflow@2.2.0, better-
    sqlite3@12.11.1, onnxruntime-node@1.30.0, protobufjs@7.6.6
```

The verifier never approves them. Approval permits commands with the host user's
permissions — that is the user's decision, and the report's job is to surface it
rather than absorb it.

## 3. The subject survey

The specification asks for a by-product: how many packages claiming to be DSH
plugins actually are. `packages/collector/src/survey.ts` answers it from
registry metadata alone — no container — and `docs/survey/` holds the raw output.

Over the first 250 packages under the npm `dsh-plugin` keyword, against
`0.2.0-rc.2`:

| | Count |
|---|---|
| Reachable | 250 |
| **Declares an installable bundle** | **240 (96%)** |
| — of those, peer-compatible with the pinned runtime | **130 (54%)** |
| — **would be refused at install** | **110 (46%)** |

All 110 are genuinely unsatisfied ranges; **zero** were grammar this evaluator
could not read, so the figure is a fact about the ecosystem rather than an
artefact of the tool.

Two consequences:

1. **Declaring a bundle is not being installable.** Nearly half of this sample
   declares an installable bundle and is still refused, because its
   `peerDependencies` were written against an older DSH generation. That gap is
   the number worth publishing, not the 96%.
2. **The npm keyword set is not the GitHub topic.** The topic is described as
   very noisy; the registry keyword set is the opposite, at 96%. The two are not
   interchangeable subject sources, and this project had been treating them as
   though they were.

`packages/collector/src/semver.ts` makes that possible by predicting DSH's own
install decision. It is checked against **four decisions DSH actually made in
the container**: find-plugin refused, cost-meter installed, the replay adapter
refused at `0.0.1-rc.1` and installed at `0.2.0-rc.2`. A range outside its
grammar is reported as `unsupported` rather than assumed compatible.

### Two traps the survey had to avoid

| Source | 250 packages | Carries `dsh`? |
|---|---|---|
| full packument | **>12 minutes** | yes |
| `/{name}/latest` | **26 seconds** | yes |
| abbreviated metadata | smallest | **no** — strips it |

The abbreviated form makes every package look like it declares no bundle. That
trap already produced a wrong survey in this project once (`V1.md` § F-V1-4), so
it is called out in the code where someone might reach for it.

## 4. The measurement that justifies the pre-filter

`@morlay/session-branch@0.1.5` declares no `dsh.bundle.patch`. It is not a
plugin. The first batch published L1–L6 **all passing** for it: it installs as a
plain dependency, is never composed, and every dimension measured the absence of
the subject and reported it as success.

That is the **second false pass** this project has produced, and both had the
same shape — *a pass derived from the absence of a failure rather than the
presence of the subject*.

It cost 94 s to produce that. With `declaresBundle()` gating both the merge and
the container launch, it now costs a metadata read. That row is the pre-filter's
justification, and it was found by measuring rather than by reasoning.

## 5. Verified / not verified

**Verified:** a 20-subject batch completes in CI within budget; per-subject cost
is ~94 s and predictable; a failing subject does not abort the batch; the L0
pre-filter prevents both a false pass and a wasted container; the survey figure
is reproducible in 26 seconds; the SemVer evaluator matches DSH's real decisions.

**Not verified:** behaviour with concurrency above 1; the per-subject ceiling
(no subject has hit 420 s); retry behaviour.

**Not implemented:** retry-once-then-abandon; a curated pool with priority
ordering; anything that notices a verified subject has since been republished.

## 6. Remaining

1. **Retry policy** — retry once, then record `inconclusive`.
2. **Concurrency** — now a decision with numbers behind it: sequential is
   ~94 s/subject, and because the setup is fixed, a concurrency of 4 would cut a
   20-subject batch to roughly 8 minutes.
3. **Curated pool** — the specification's "curated pool first, then on demand".
   The survey provides the candidate list; nothing yet ranks or schedules it.
4. **Staleness** — a report is a snapshot, and nothing yet notices that a
   verified subject has since been republished.

## 7. Reproduce

```sh
# the survey: registry metadata only, no container, no credential
node packages/cli/src/main.ts survey --query 'keywords:dsh-plugin' --limit 250 \
  --runtime 0.2.0-rc.2 --out docs/survey/npm-dsh-plugin-250.json

# a batch
gh workflow run verify.yml -f dsh_version=0.2.0-rc.2 -f verify_specs='<spec>,<spec>,...'
gh run download <run-id> -n exec-reports
cat .verify/reports/timings.tsv          # per-subject cost

node --test packages/report/test/*.test.ts packages/collector/test/*.test.ts
```
