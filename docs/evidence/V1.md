`@morlay/session-branch` is the L0 filter doing its job: an npm package
published under the plugin keyword, with 15 files, that declares no
`dsh.bundle.patch` and therefore is not an installable DSH plugin at all. That
is the same gap the ecosystem research points at, reproduced on demand in under
a second.

`dsh-pet@0.3.1` is the cost finding: it fetched in **98.3 s against a 120 s
ceiling** — 22 seconds from a `timeout` conclusion. A verification product that
had no budget would have stalled on it instead.

## 4. Why `runtime.dshVersion` says `not-executed`

L0 and L4 download a tarball and read it. That is **not** executing it, which is
precisely why these two dimensions need no container and can run anywhere —
including the machine that drafted them, which holds real credentials.

The consequence is stated in the report rather than papered over: nothing ran,
so `runtime.dshVersion` is `not-executed` and every execution dimension is
`skip`. The verdict is capped at `partial` by construction, and the validator
enforces that cap.

## 5. Shortfalls against the stated evidence requirement

Recorded rather than smoothed over:

1. **No DSH kernel version in a static report.** The specification asks each
   report to carry the plugin hash, the verifier version, *and* the DSH version.
   The first two are present (`subject.integrity`, `verifier.version` +
   `verifier.commit`). The third is `not-executed`, because no DSH runtime was
   involved. It becomes a real version only when L1/L2 run in the container.
2. **No sampling data points.** The specification lists sampling points among
   required evidence. L5 has not been implemented, so there are none to publish.
   Manufacturing representative numbers would be exactly the failure this
   project exists to oppose.

## 6. Findings

**F-V1-1 — the validator caught three of my own defects.** A `reportId` pattern
that forbade `:`; an `excerptBytes` computed from a different string than the
excerpt; and an `async` helper leaking a `Promise` into `subject.integrity`.
None was caught by a type checker, because there is no type gate. This is the
concrete cost of limit **F7** in `docs/method.md`: with `tsc --noEmit` the third
would have been a compile error. Installing a compiler in PR CI would either
trip the execution policy or require weakening it, so the trade-off stands for
now — but it is now backed by evidence rather than speculation.

**F-V1-2 — a real false positive, found on the first live subject.**
`dsh-find-plugin@0.4.0` produced a `writes_outside_workspace` finding from a
**doc comment** that mentioned `~/.dsh`. A finding a reader opens and finds in
prose is worse than no finding. Standalone comment lines are now skipped before
matching (line numbers preserved), and the whole-content fallback blanks
comments too rather than testing raw text. Regression-tested.

**F-V1-3 — evidence and attribution disagreed.** The same package ships both
`src/*.ts` and compiled `lib/*.js`. The attribution correctly said
`author-source`, but the sample shown came from `lib/`. Evidence is now ordered
author-source first, so what a reader opens matches what the report claims.

**F-V1-4 — abbreviated registry metadata hides `dsh` fields.** npm's
`application/vnd.npm.install-v1+json` representation omits the custom `dsh`
object, so a survey using it reported `patch=False` for every package. Any
future bulk scanner must use the full packument. Caught by cross-checking one
package against its full document.

**F-V1-5 — 62 MB plugins are real, and cost dominates.** `dsh-pet@0.3.1`
unpacks to 64.8 MB. At 358 KB/s this network needed 174 s; the run succeeded
here at 98.3 s. Bulk verification economics (V4) must plan around artifact
bytes, not package count.

**F-V1-6 — the repository's own hygiene scanner caught a test fixture.** The
redaction test planted a token-shaped literal, and `tools/check-hygiene.mjs`
failed the build on it. That is the scanner working as intended. The fix was to
assemble the fixture at runtime rather than to allowlist test files: a fixture
is not a good reason to weaken a check whose whole purpose is that no
token-shaped string is committed.

## 8. Verified / not verified / blocked

**Verified:** the contract rejects overclaiming; evidence rules are enforced;
redaction holds against a planted credential; L0 and L4 produce real reports on
real published artifacts; the catalog index is derived and staleness is caught;
three subjects produced reproducible conclusions.

**Not verified:** anything about installing, loading, running, the overhead of,
or uninstalling any plugin. No execution dimension has run for any subject.

**Blocked:** L3 via the official replay plugin (V0 § F2, unchanged). Execution
dimensions in general need `packages/runner` to grow a real L1/L2/L5/L6
implementation inside the container; the V0 container currently only measures a
baseline.

implementation. L1, L2 and L6 now run inside the container and have produced a

## What landed

- `packages/runner/src/execution-probe.ts` — L1 (install, with
  peer-incompatibility classification and pending build-script capture), L2
  (bounded boot), L6 (removal residue). Drives the published CLI and reads what
  it prints; it assumes nothing about the internal boot API.
- `packages/report/src/merge.ts` — combines static L0+L4 with execution
  L1+L2+L6, **recomputes** the verdict, and records L3 as blocked. A decisive
  status with no step record is downgraded to `inconclusive` rather than propped
  up with fabricated evidence.
- `verify.yml` — `exec-verify` runs static on the runner, execution in a
  one-off container, then merge and validate. Reports now carry `GITHUB_SHA`.
- 8 merge tests; 43 total.

## The finding that matters most

**DSH enforces `peerDependencies` on `@deepseek-ai/dsh*` and refuses an
incompatible install outright.** Observed in the container:

```
dsh: installation rejected: Plugin dsh-find-plugin@0.4.0 is incompatible with
dsh 0.2.0-rc.2: peerDependencies {"@deepseek-ai/dsh-tools":"^0.1.0-rc.6 || ..."}.
... dsh: nothing was installed.
```

This is the single most decision-relevant fact about that plugin, and no static
scan can see it. It also corrects a conflation in the method: `engines.dsh` is
declarative and unenforced (V0 § F1), but **peer ranges are a different
mechanism and *are* enforced**. `docs/method.md` has been corrected.

Checked across ten popular subjects, the ecosystem splits cleanly:

| Subject | `dsh-*` peers | Installs on 0.2.0-rc.2 |
|---|---|---|
| `dsh-cost-meter@1.8.8` | allow `>=0.2.0-rc.1` | **yes** — verified |
| `dsh-find-plugin@0.4.0` | allow `^0.1.x` only | **no** — refused |
| `dsh-tiddlywiki`, `dsh-whale-widget` | none declared | expected yes |
| `@deepseek-ai/dsh-llm-replay@0.0.1-rc.1` | `^0.0.1-rc.1`, one peer absent from npm | **no** — refused |

**L3 is therefore blocked with observed evidence, not inference.** The
sanctioned key-free path cannot be installed, so no session can be driven
without a credential, and none is injected.

## Defects found by actually running it

Five, none of which the fixtures caught. They are the argument for the whole
approach, so they are recorded in full.

1. **The profile path was wrong.** It read `$DSH_HOME/<name>`; DSH uses
   `$DSH_HOME/profiles/<name>`. Every profile read returned null, which silently
   turned L6's "no residue found" into a claim about a directory that was never
   inspected. **This is the worst kind of bug this project can produce**: a
   confident pass resting on nothing. L6 now reports `inconclusive` when it
   cannot read the profile.
2. **A graceful shutdown was read as a crash.** DSH installs a SIGTERM handler
   that exits **0**, so a healthy boot that hit the bound looked like an early
   exit, and a load *failure* was reported for a healthy plugin.
3. **A plugin's success message was read as an error.** The classifier assumed a
   clean composition is silent. `dsh-cost-meter` prints
   `[dsh-cost-meter] 已加载,账本:…` ("loaded, ledger: …") and was reported as a
   load failure. Output is not error; the classifier now keys on failure-shaped
   diagnostics.
4. **`runtime.os`/`arch` written as `undefined`**, which the schema rejects —
   caught by a merge test.
5. **A claimed pass with no step record** produced dangling evidence references
   — also caught by a merge test, and now downgraded to `inconclusive`.

Defects 2 and 3 were both *false failures*, which is the safer direction to err,
but 1 was a false pass, which is not.

## Verified / not verified

**Verified:** the execution path runs end to end in a one-off container with no
credentials; install refusal and success are distinguished from the CLI's own
output; a healthy boot is distinguished from a failed one; removal residue is
checked in the right directory.

**Not verified:** runtime overhead (L5, unimplemented), and any session
behaviour (L3, blocked). The L2 conclusion rests on exit behaviour and the
absence of failure diagnostics, not on a directly read fiber phase — stated in
the report's `limits[]`.
