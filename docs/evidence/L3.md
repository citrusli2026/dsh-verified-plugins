# L3 — a keyless session: the conclusion was wrong, and why

**Status: RESOLVED — L3 runs, and the first `verified` report is published.**
The project's earlier "blocked" conclusion was incorrect and is retracted here.

`docs/evidence/V0.md` § F2 and `docs/method.md` § 5 F2 both stated that L3 was
blocked because the official key-free replay plugin could not be installed
against DSH `0.2.0-rc.2`. That is wrong. It was reached by examining the version
npm's `latest` dist-tag resolves to, which belongs to a much older runtime
generation. The version matching the pinned runtime exists, installs cleanly,
and every binding it imports is present.

This record exists because a wrong conclusion that is quietly deleted is worse
than one that is corrected in public — the same rule the reports follow.

---

## 1. What was claimed, and what is true

| Claim | Verdict |
|---|---|
| `@deepseek-ai/dsh-llm-replay` cannot be installed on `0.2.0-rc.2` | **Wrong** — `0.2.0-rc.2` installs cleanly |
| Its declared peers cannot be satisfied | True of `0.0.1-rc.1`, false of `0.2.0-rc.2` |
| Two imported bindings do not exist in `0.2.0-rc.2` | True of `0.0.1-rc.1`'s **import list**, false of `0.2.0-rc.2`'s own |
| L3 is blocked | **Retracted** — the path is open; the fixture remains to be authored |

## 2. Root cause

`@deepseek-ai/dsh-llm-replay` publishes 32 versions. Its dist-tags are:

```
latest: 0.0.1-rc.1      <- what `npm install <pkg>` gives you
next:   0.2.0-rc.2      <- the version that matches the pinned runtime
alpha:  0.2.1-alpha.1
```

`latest` points at `0.0.1-rc.1`, a version from a much older runtime generation
whose peers are `^0.0.1-rc.1` ranges that no current runtime can satisfy. The
project resolved the package by bare name, got `0.0.1-rc.1`, observed both the
peer refusal and the missing bindings, and concluded the *capability* was
blocked rather than the *version*.

### Why the binding analysis was convincing and still misleading

`0.0.1-rc.1` imports `assertNever` from `@deepseek-ai/dsh-llm` and
`decodeStorageRecord` from `@deepseek-ai/dsh-session`. In `0.2.0-rc.2`:

- `assertNever` **moved** to `@deepseek-ai/dsh-util-values`; `dsh-llm` imports it
  but no longer re-exports it;
- `decodeStorageRecord` has **zero occurrences** in `dsh-session` — replaced by
  the session-format catalog.

So the missing-bindings finding was real, and it was real *about the wrong
version*. `0.2.0-rc.2` imports neither of those from those places: it takes
`SESSION_FORMAT_VERSION`/`SessionLogOffset` from `dsh-session`,
`assertNever` from `dsh-util-values`, and seven bindings from `dsh-llm`. All
four packages export everything it asks for (checked exhaustively against the
container's modules).

**This is exactly the failure mode the project exists to surface, and it caught
the project itself.** A package whose default install path yields a version that
cannot work, with nothing in the package's own metadata saying so.

## 3. Evidence

### Static — every required binding exists

| Package | Required | Result |
|---|---|---|
| `@deepseek-ai/dsh-session` | `SESSION_FORMAT_VERSION`, `SessionLogOffset` | all present (28 exports) |
| `@deepseek-ai/dsh-session-format-catalog` | 3 bindings | all present |
| `@deepseek-ai/dsh-llm` | 7 bindings | all present (66 exports) |
| `@deepseek-ai/dsh-util-values` | `assertNever` | present |

### Observed in the container (`l3-probe` job)

```
dsh plugin --profile l3 add @deepseek-ai/dsh-llm-replay@0.2.0-rc.2
  Packages: +18
  dependencies:
  + @deepseek-ai/dsh-llm-replay 0.2.0-rc.2
  Done in 809ms using pnpm v12.8.1
### exit=0
```

No peer rejection. Compare with the same command on the default version, which
is refused outright.

### A headless profile can be created

```
dsh --profile l3h --from-default-profile headless
-> bundles: ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-headless"]
```

### One nuance that matters

```
dsh: warning: @deepseek-ai/dsh-llm-replay declares no dsh.bundle
     — installed as a plain dependency, not a profile layer
```

The replay plugin is **not a bundle**. Installing it does not add it to the
composition. It is a plain dependency that must be mounted as a loader entry —
which the CLI supports through `--patch <path>`, "extra patch-list overlay
applied after the profile layer (repeatable)".

## 4. How L3 was actually solved

### The fixture needed no session log at all

The plan was to author a session JSONL. Reading the plugin's own
`readPrimaryFixture` showed a shortcut: when `config.file === config.overrideFile`
it treats the sidecar as the whole script, so **a bare `ReplayEntry[]` replaces
the JSONL path entirely**. That matters beyond convenience — obtaining a real
recording requires driving the agent against a provider, which needs a
credential this project never injects a fixture.

Two further version traps were caught by reading the 0.2.0-rc.2 **code** rather
than the README, which documents the older generation:

| The README says | 0.2.0-rc.2 actually reads |
|---|---|
| derive from `assistant/chunk` events | `assistant/message` / `assistant/attempt` with a compact `stream` |
| the compaction event is `compact/summary` | `compaction/summary` |

Both README claims were true of `0.0.1-rc.1` — the version `latest` resolves to.
That is the same trap as § 2, encountered a second time in the same
investigation.

### Mounting

The plugin declares no `dsh.bundle`, so installing it does not compose it. It is
mounted as a loader entry through an `--patch` overlay, using the `insert` form
taken from a shipped bundle patch rather than a guessed shape. The adapter is
installed at the **discovered runtime version**, so the pairing cannot drift.

### The result

```
dsh --profile l3run --patch /work/fixtures/replay/l3-overlay.yml --json "reply with any text"

{"type":"status","phase":"turn_end","turn":1,"reason":{"kind":"completed"}}
{"type":"final","text":"Replay fixture: no provider was called."}
### exit=0
```

The session ran with the subject installed in the same headless profile, so the
result is attributable to it. No credential was present and no provider was
contacted.

`catalog/npm/dsh-cost-meter.json` is now the first **`verified`** report: all
seven dimensions pass. Every L3 pass carries the limit that it ran against a
replayed transcript, not a provider — it establishes that a session completes
without a credential, not that the subject behaves correctly against a live
model.

## 5. Process note

Three things went wrong and are worth naming, because the second and third are
the project's own rules applied to itself:

1. **Resolved by bare name.** `npm view <pkg> version` reports the `latest`
   tag, not the version compatible with a pinned runtime. Any tool that resolves
   plugins for a pinned runtime — including this one — must read the full
   version list and the dist-tags, never the default resolution.
2. **A conclusion was drawn from one version pair and stated as a capability
   limit.** The evidence was about `0.0.1-rc.1`; the claim was about the
   capability. "Blocked" was recorded at all three levels of the repo before the
   version space was enumerated.
3. **The correction is public.** V0's F2 and method's F2 are annotated rather
   than rewritten, so a reader who saw the earlier claim can find out it changed
   and why.
