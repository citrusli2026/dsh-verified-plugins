## 2. How it measures

`process.getActiveResourcesInfo()`, `process.report.getReport()` and
`process.memoryUsage()` describe *their own* process, so the sampler is injected
into the host with `NODE_OPTIONS=--import`. Sampling from outside would measure
the observer.

`NODE_OPTIONS` is inherited, so the sampler also loads in every Node child the
host spawns. It claims an exclusive lock (`SAMPLE_OUT.lock`, opened `wx`): the
first process to load it samples, and every child exits quietly instead of
overwriting the file. Without that, the last child to exit would win.

Ordering, per the specification: the **baseline** profile — which contains no
subject — is sampled first, then the subject is installed and the **activated**
profile is sampled. Same container, same order, 3 runs each, median within a run
and median across runs.

### Thresholds

Deliberately coarse. The specification's examples are order-of-magnitude watcher
changes, RSS growth beyond 100 MB and start-up increases beyond 2 s; anything
finer on a shared CI runner is noise dressed up as measurement.

| Metric | Fires when |
|---|---|
| `watchers` | at least doubled **and** up by 5, or up by 10 outright |
| `libuvHandles` | at least doubled **and** up by 20 |
| `activeTotal` | at least doubled **and** up by 10 |
| `timers` | up by 20 |
| `rss` | up by more than 100 MiB |
| `fds` | up by 50 |
| `atMs` (time to steady state) | later by more than 2 s |

## 3. Acceptance: the watcher anomaly is caught

The specification's criterion is to reproduce the recursive-watcher failure and
catch it reliably. Rather than run a real such plugin — third-party code, and
this workspace holds credentials (`docs/security.md` § 5) — the test uses two
controlled hosts:

```
watcher-acceptance: baseline median=0 activated median=60 (3 runs, 60 watched dirs)
rule fired: true
OK: the watcher anomaly is caught
```

**It is non-vacuous, and that was checked rather than assumed.** Restoring the
wrong handle spelling that caused the original miss (see F-V3-2) makes it report
`baseline median=0 activated median=0`, `rule fired: false`, and exit 1.

It lives at `tools/acceptance/watcher.mjs` and runs on every pull request.

## 4. The measurement on a real subject

`dsh-cost-meter@1.8.8`, 6 sampled runs (3 baseline, 3 activated):

| Metric | Baseline | Activated | Delta |
|---|---|---|---|
| RSS | 199.5 MB | 231.1 MB | **+31.6 MB** |
| heapUsed | 68.4 MB | 84.5 MB | +16.0 MB |
| libuv handles | 22 | 23 | +1 |
| libuv active handles | 17 | 19 | +2 |
| active resources | 10 | 11 | +1 |
| filesystem watchers | 7 | 8 | +1 |
| open descriptors | 20 | 20 | 0 |
| time to steady state | 8032 ms | 8048 ms | +16 ms |

**Result: `no-significant-delta`.** No metric cleared a threshold, so none is
claimed. The +31.6 MB RSS is real and consistent across runs, and it is
deliberately *not* reported as a finding: it is below the significance bar, and
the number itself is published in `overhead.delta` for a reader who disagrees
with the threshold.

The baseline host holds 7 filesystem watchers of its own
(`FSEventWrap: 7`, `PipeWrap: 3`). That is what a DSH host looks like before any
plugin is involved, which is exactly why the comparison is differential rather
than absolute.

## 5. Findings

**F-V3-1 — the libuv section is an array, not an object.** The first
implementation read `report.libuv.handle.count`, which does not exist; the
section is an **array** of `{type, is_active, is_referenced, address}`. Every run
reported `libuvHandles: null` — a metric that looked measured while carrying no
data. Both shapes are now handled so a Node change cannot quietly reintroduce
the silent null.

**F-V3-2 — the watcher handle has a different name than assumed.**
`getActiveResourcesInfo()` reports a live filesystem watch as `FSEventWrap`, not
`FSEvent` or `StatWatcher`. The counter therefore reported **0 watchers on a host
holding seven**, and would have missed the exact failure the specification cites.
Found by publishing `resourceKinds` and reading it — the count alone looked
plausible. This is the bug that motivated § 3.

**F-V3-3 — `NODE_OPTIONS` is inherited.** The sampler loaded in every Node child
the host spawned, and the last child to exit would have overwritten the sample
file. Fixed with an exclusive lock.

**F-V3-4 — a metric count is not evidence.** `activeTotal: 11` says nothing about
what a plugin holds open. The report now carries `overhead.resourceKinds` for
both passes, which is how F-V3-2 was found at all.

## 6. Limits, stated

1. **Thresholds are coarse and unnormalised.** A +31.6 MB RSS delta is reported
   as a number but not as a finding. Byte-for-byte comparability across subjects
   of very different sizes is not attempted, and no score exists.
2. **One container, one machine, one point in time.** Numbers move with runner
   load; 3 runs and a median mitigate but do not remove that.
3. **The container is not resource-limited in this measurement.** The
   specification's ceilings are enforced for wall clock and artifact size, but
   L5 does not yet pin CPU or memory, so a subject cannot be measured under a
   constrained budget.
4. **`atMs` is time-to-steady-state, not boot time.** It measures from process
   spawn to the sampler's first sample, which includes a fixed 6 s settle.
5. **L5 passing does not make a report `verified`.** L3 remains blocked
   upstream, so every published verdict is still capped at `partial`.

## 7. Verified / not verified

**Verified:** the differential runs in the container; both passes produce
consistent medians; the anomaly detector fires on a real watcher load and is
mutation-tested; a null result is published as `no-significant-delta` rather
than elided.

**Not verified:** cross-platform behaviour (Linux/x64 only), behaviour under
resource constraints, and whether any *specific* real plugin has a problematic
overhead profile — one subject has been measured, and it has none.
