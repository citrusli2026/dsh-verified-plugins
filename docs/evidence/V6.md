## 2. Freshness, and the first thing it found

Nothing previously noticed that a verified subject had been republished. On its
first run the check found a real case:

```
current 23  stale 1  unknown 0
  stale  npm:dsh-cost-meter@1.8.8 — a newer version is published: 1.8.9
```

`dsh-cost-meter@1.8.9` was published within hours of the `1.8.8` verification.
That is the mechanism working on a live ecosystem rather than on a fixture.

### Where it lives, and why not in the report

Staleness is written to **`catalog/staleness.json`**, not into the reports and
not into the index:

- a report is the immutable record of what was run; rewriting one to say "stale"
  would corrupt the evidence, which is the whole product;
- the index is derived from the reports alone so CI can re-derive and
  staleness-check it **offline**. Folding a network read into it would make that
  check slow and flaky.

Three states, because two would force a guess: `current`, `stale`, `unknown`
(the registry could not be read — which is not the same as current).

**A stale report is not a wrong report.** It describes a version that is no
longer the latest, and its findings still hold for that version. Both the site
and the artifact say so, because the alternative reading — "this plugin got
worse" — is available to a careless reader.

## 3. Corrections are additive, mechanically

`changelog` and `supersedes` had been in the schema since V1 and unused. The
`amend` command now wires them up:

```sh
node packages/cli/src/main.ts amend <new.json> --previous <old.json> \
  --change "why the conclusion changed"
```

Four refusals make the rule real rather than advisory:

| Refusal | Why |
|---|---|
| **fewer evidence entries** than the superseded report | dropping evidence is a retraction of the record, not a correction |
| a different package | a correction must cover the same subject |
| the same `reportId` | a report cannot supersede itself |
| no stated reason | "why" is the one thing a diff cannot know |

And one property that removes the author's discretion entirely: the
`changeDescription` is **computed by reading both reports**, so a changelog
cannot be published that misdescribes the change it records. A test constructs a
no-op amendment and asserts the changelog says `no dimension status changed`
rather than accepting the author's claim that "everything changed".

**A bug this caught:** the first implementation seeded the changelog from the
*incoming* report, so a second correction silently erased the first. The
history now accumulates across the chain, deduplicated by `date|change`. Found
by a test that amended twice and asserted a length of two.

## 4. The false positive / false negative catalogue

`docs/method.md` § 6 lists every failure this verifier has actually had, how it
was found, and whether it is fixed — eight false positives and four false
negatives, plus six limits that are not defects.

The entries are grouped by severity, because the distinctions matter:

> A false failure is annoying. A **false pass** is the thing that makes a
> verification product worse than useless, because it launders an absence of
> evidence into a claim.

Three false passes are on the list. Two are fixed (the profile-path bug that
made L6 inspect the wrong directory; the non-bundle subject that collected
L1–L6 passes while never being composed). One is **open** and stated in every
report: L2's conclusion is inferred from the absence of failure diagnostics
rather than from a directly read fiber phase.

The pattern behind both fixed ones is recorded in the document, because it is
the failure mode this project is most likely to repeat:

> **a pass derived from the absence of a failure rather than the presence of the
> subject.**

## 5. The appeal process

`docs/appeals.md` states the process, the four things an appeal must supply, and
— more usefully — what is **not** appealable:

| Appealable | Not appealable |
|---|---|
| A dimension status a re-run contradicts | A verdict you dislike that the dimensions support |
| A capability finding that is a false positive | A finding you consider harmless — capability is not intent |
| A misreported install failure | Our choice of runtime, or that DSH enforces peers |
| A `stale` marking that is wrong | A `stale` marking that is right |

The line is whether the **method** was misapplied. "You ran it wrong" is
appealable; "I don't like what you observed" is not.

The document also points at this project's own retraction
([`L3.md`](L3.md)) as the worked example of the rule applying to itself.

## 6. Verified / not verified

**Verified:** staleness is assessed from the registry in ~3 seconds for 24
reports and finds a real case; the site renders freshness and a banner; the
amendment guards refuse all four invalid changes and the changelog accumulates;
80 tests pass.

**Not verified, and stated plainly:**

1. **No external appeal has ever been filed.** The process is documented, the
   template exists, and the tooling is tested — but it has not been exercised by
   a third party. A process that has never run is a claim, not evidence.
2. **Staleness is version-based.** A republished artefact at the *same* version
   (a registry yank-and-replace) is not detected; the recorded integrity hash
   would differ, but nothing compares them yet.
3. **Nothing schedules the check.** `stale` is a maintainer command, like the
   survey and the deploy. The nightly `verify.yml` schedule re-runs the
   *container baseline*, not the catalogue.

## 7. Remaining, after V6

- Automate the staleness check and the deploy (both currently maintainer steps,
  for the same reason: no workflow holds a write token).
- Compare recorded integrity against the registry's for same-version
  republishes.
- Exercise the appeal process once, so it stops being untested.

## 8. Reproduce

```sh
node packages/cli/src/main.ts stale --runtime 0.2.0-rc.2 --out catalog/staleness.json
node packages/cli/src/main.ts site --out site-dist          # renders freshness

# the guards
node packages/cli/src/main.ts amend new.json --previous old.json --change "why"
node --test packages/report/test/*.test.ts packages/collector/test/*.test.ts
```
